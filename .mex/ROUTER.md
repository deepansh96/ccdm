# Session Bootstrap

If you haven't already read `AGENTS.md`, read it now — it contains the project identity, non-negotiables, and commands.

Then read this file fully before doing anything else in this session.

## Current Project State
**Working:**
- Codex Discord MCP registration runs under a per-Codex-Home `config.toml.lock` shared by bridges and `start-codex-session.sh`; a bridge whose app-server still loads a foreign `discord-*` server after reload fails startup before its Router hello.
- Router message ingress accepts only Discord default (0) and reply (19) messages before any session or observer routing; system notices, including thread-created (18), thread-starter (21), and pins (6), are dropped. The E2E harness supports thread channels, Gateway lifecycle events, thread REST operations, audit logs, and thread-scoped webhook messages. The Router recognises public threads (type 11) under a registered, non-`remote:` project channel and serves a `thread` role (`keys/.thread-<thread_id>.key`, checked once at hello, `unauthorized`/`not_a_project_thread`, newer hello `replaced`): owner and current parent-guest messages, `/compact`/`/pause`/`/unpause` commands and reactions reach only that thread's listener; `/close`, `/config`, `/restart`, `/clear` reach no session; replies and edits use the parent webhook with `thread_id` under `<project>-<thread provider> · N%`. Observer frames carry `conversation_id` (and `thread_id` in threads). A thread session's Session Scope is its thread alone for every op (reads, exports, attachments, react, typing, reply, edit): the parent, a sibling, a root channel, a parent message and the starter (whose id is the thread id) are `scope_violation`. A changed or missing `.thread-<id>.key` revokes that thread with `key_rotated` (a project key rotation leaves threads connected); a reload revokes thread connections with `deregistered` or, when the parent's `channel_id` moves, `project_moved`, and a `webhook_id` change only updates the route; no `scope_changed` ever reaches a thread connection. The owner's bot mention or native reply to a root-bot message in an eligible thread reaches root with the thread as `channel_id` (a guest's reaches no one), and root's ops accept an eligible thread id. `router status` prints a `thread <project> thread=<id> provider=<p> connected=<at>` line per thread listener. A single `supervisor` role (its key is `.supervisor.key` in the Router keys directory; a newer hello `replaced`; `hello_ok` carries `bot_user_id` and each project's `{project, channel_id, webhook_id}`) receives `thread_message` for every type 0/19 message in an eligible thread (with `delivered_to_session` and `author_class` `owner`/`guest`/`root_bot`/`project_webhook`/`other`), `thread_command` for `/close`, `/config…`, `/restart`, `/clear` (and `/compact`/`/pause`/`/unpause` with no live thread session), `channel_command` for owner/guest `/thread …` and `/config …` in a project channel (never the Channel Conversation), `thread_reaction` (thread reactions also reach the thread session and the observer with `conversation_id`), `thread_create`/`thread_update`/`thread_delete` for eligible threads, `gateway_resumed` on `shardResume` and post-ready `shardReady`, and `thread_session_live` (pushed in the same turn the thread listener registers) / `thread_session_revoked` (`replaced`, `key_rotated`, `deregistered`, `project_moved`, `disconnected`). An owner or guest thread message no session or supervisor takes, and a channel `/thread`/`/config` with no supervisor, get 💤. `router status` prints `supervisor: connected connected=<at>` or `supervisor: absent`. Supervisor-only ops (`forbidden` to every other role), each confined to a registered, non-`remote:` project channel or a public thread under one (anything else is `scope_violation`) and sent with the root token through the shared REST queue under the client's deadline: `thread_create` (a standalone type-11 thread with `auto_archive_duration: 10080`), `thread_update` (PATCHes only `archived` and `auto_archive_duration`), `thread_list` (active guild threads under eligible parents, or one `channel_id`, plus archived public threads per parent within `archived_within_days`, at most 10 pages of 100), `thread_history` (`limit` ≤ 100, `before`, with `author_class`), `thread_message_get` (a starter message from the parent channel), `thread_archive_actor` (action-111 audit-log entries for the thread since `since`, or `{forbidden:true}`), `thread_react`, `thread_notice` (a root-bot post with `allowed_mentions:{parse:[]}`), `thread_revoke` (revokes the thread's listener and op-only connections with the given reason) and `thread_request_done`. A channel session's `create_thread` (own channel only) pushes `thread_create_request` with a `request_id` and `requester:{kind:"channel-agent", project}` to the supervisor and waits for `thread_request_done` until its deadline (`timeout`); with no supervisor, or when the supervisor goes while it waits, it fails with `supervisor_unavailable`. The Thread Supervisor runs in the foreground with `scripts/thread-supervisor.py` (`run`; `status` reports the worker, its Router connection, the store version and bound threads per project; no installer yet): a Python worker (`scripts/thread_supervisor/`, one module per concern behind a thin event table) holds an exclusive `worker.lock` (a second worker exits 2), keeps a private SQLite store (`threads.sqlite3`, WAL, `synchronous=FULL`, `secure_delete`, `user_version` 1, tables `threads`, `creation_requests`, `boot_buffers`, exact columns verified) in the private thread-supervisor state directory under ~/.local/state/ccdm (0700/0600; `CCDM_THREAD_SUPERVISOR_STATE_DIR` or `--state-dir` override), writes a fresh `.supervisor.key` on each start, and spawns `scripts/thread-supervisor-link.js`, which holds the one `supervisor` Router connection through `RouterClient` and relays events and op calls as NDJSON over stdio. It holds no Discord credential and calls Discord only through Router ops. On `thread_create` it binds, idempotently by thread id, a thread created by the parent's owner or a current guest (then PATCHes it through `thread_update` to `auto_archive_duration: 10080`) or by the root bot for a pending creation request of that project and name (taking its overrides); any other creator binds nothing. `/thread <name> [--provider|--account|--model|--effort] [first message…]` in a project channel (owner or guest, a `channel_command` that never reaches a model) and `scripts/threads.sh create <project> <name> [flags] [message]` (requester `root`, through the supervisor's private 0600 `control.sock` in its state dir) run one creation flow: the flags are validated (provider `claude` or `codex`; an account alias in that provider's `claude_accounts` or `codex_accounts`; a model name; a Claude effort `low|medium|high|xhigh|max` or a Codex effort `none|minimal|low|medium|high|xhigh`), a pending `creation_requests` row is stored, `thread_create` makes the thread (10080 minutes) and the request records its id, and a root-bot notice in the thread lists the settings and any first message; binding stores the `resolved_*` settings and, with a first message, starts the session at once with that message as the starter (no 👀). A validation failure creates nothing: `/thread` posts `Thread not created: <reason>` in the channel, and `threads.sh` exits 2 (1 when no supervisor answers). The launcher gets the resolved provider, account, model and effort. A channel session (the Claude channel server in channel mode, or a Codex project's Discord MCP server; never a thread or root) exposes `create_thread {name, provider?, account?, model?, effort?, first_message?}`, which calls the Router's `create_thread` on its own channel (another `chat_id`/`channel_id` is `scope_violation`) with a 60 s budget; the supervisor answers `thread_create_request` (requester `channel-agent`) through the same creation flow with `thread_request_done` (`ok` and `thread_id`, or error code `invalid` with the reason, creating nothing), and the tool returns `created thread (id: <thread_id>)` or the op error (`supervisor_unavailable` with no supervisor). An owner or guest message in a registered thread (or one whose last start failed; commands and bot mentions never trigger) boots a Claude Thread Conversation: 👀 on the trigger, the row `booting`, every owner or guest `thread_message` buffered, and `scripts/start-thread-session.sh <project> <thread_id> --provider claude [--account|--model|--effort]` launched with `CCDM_THREAD_BOOTSTRAP_FILE` (fresh `keys/.thread-<thread_id>.key`, launch dir `launches/<project>/threads/<thread_id>/`, tmux `<screen>-t-<last6>`, `zsh -ic` in the project path, refused while a process carries that key path, cleaned up on failure, printing `{pid, provider_conversation_id, tmux, provider_home}`; an account is a `claude_accounts` alias, else the project's `claude_home`, else the default). On `thread_session_live` the supervisor writes the bootstrap `{preamble, starter, messages[], included_message_ids[]}` atomically (0600; the starter is the parent message read with `thread_message_get`, else empty), removes 👀 and sets `live`; the Claude session id goes to the supervisor store, never the registry. A launch failure, an early exit or the boot timeout (`CCDM_THREAD_BOOT_TIMEOUT_S`, default 120 s) removes 👀, posts a one-line root-bot notice and sets the row `stopped` with stop reason `start-failed`; the next eligible message retries. The channel server in thread mode (`CCDM_THREAD_ID`, `CCDM_THREAD_PROVIDER`, `CCDM_THREAD_BOOTSTRAP_FILE`) says hello as `thread`, holds live events until the bootstrap exists, delivers it as the first notification and drops held messages it includes, ignores `scope_changed`, records no reminder events, and reads its context percentage from the thread launch dir (the statusline maps a `.thread-<id>.key` there). A thread whose provider is Codex (its override, else the project's `type`, so a Claude project can have one) boots the same way with `--provider codex`: the supervisor first allocates it a `ws_port` from base 19000 (`CCDM_THREAD_WS_PORT_BASE`), skipping every registry `ws_port`, every port a store row holds and every port in use, records it on the row and passes it as `CCDM_THREAD_WS_PORT`; the launcher resolves the Codex Home with `resolve-codex-home.py <registry> <project> --account <alias>` (the thread alias in place of the project's `codex_account`; an unknown alias fails the start) and runs `codex-bridge.js` in thread mode, printing `ws_port` too and the Codex thread uuid as `provider_conversation_id`. The bridge in thread mode says hello as `thread` (`CHANNEL_ID` is the thread id, launch dir the thread's), registers MCP `discord-<thread_id>` under the per-Codex-Home lock with post-reload verification, whose scoped server connects as `thread` with `listener:false`, sends the bootstrap (after the transport instruction) as its first turn in place of the READY turn, and holds live events until then, dropping messages the bootstrap includes. `/thread`, commands, lifecycle, capacity, resume and reconcile are not built yet.
- The Router is the only transport: registry readers ignore `transport`, and no script outside root admin reads a pool bot token. Guest management, operator exports, and usage reporting read only the root token from root Discord state; guest grants and revokes write no per-bot access file and make no `project-bot` calls. The Conversation Reminder observer has no Gateway login of its own and sends only as root.
- Root bot serves every registered project channel through the Router, each with its own webhook identity.
- The Router (`scripts/router.js`) serves every registered project with the root token: it forwards owner and guest messages, plain management commands, and reactions over a private NDJSON Unix socket to the one keyed session per project, marks messages to offline channels 💤 without replay (a project without `webhook_id`, not yet migrated and possibly still on its pool bot, is dropped silently instead), posts `reply` through the project's `ccdm-<project>` webhook as `<project>-<type> · N%` (with files, a jump link for `reply_to`, and chunking past 2000 characters), edits only the project's own webhook messages, reacts and types as the bot, reads its channel (`fetch_messages`, `read_last_x_messages_in_channel` with reads over 100 returned as a private 0600 transcript path, and `export_message_range` in the export tool's format), hands back a signed CDN URL for `download_attachment` (reusing a delivered event's URL while fresh, otherwise re-fetching the message), rejects out-of-channel operations and `message_id` targets outside the session's channel as `scope_violation`, and reports health and recent scope violations with `router status`. A newly written project key revokes (`revoked` event, then disconnect) the session holding the old key, and a newer hello replaces the previous listener. Malformed frames get `malformed_frame` without dropping the connection, pre-hello requests get `not_authenticated`, and a wrong protocol version gets `hello_error`. The client library reconnects with capped exponential backoff (500 ms doubling to 30 s, overridable by `CCDM_ROUTER_RECONNECT_MIN_MS`/`_MAX_MS`), fails requests with `router_unavailable` while disconnected without queueing, and ends for good on revocation. `ensure-webhook <project>` records `webhook_id` in the registry and keeps the token only in private Router state, and `delete-webhook <project>` deletes the webhook and its token and clears `webhook_id` (a rerun is a no-op). A webhook deleted in Discord is recreated once on the next `reply`, which updates `webhook_id`, runs the reminder `assignment-changed`, and retries; a second deletion in a row fails with `webhook_deleted` instead of recreating again. A lost token with a known `webhook_id` is refetched through the bot. Discord rate limits stop at the Router: REST is queued per route bucket (bucket headers, `Retry-After`, and the global limit), repeated `edit_message` calls to one message coalesce to the latest content, and a request still limited after the wait bound (`CCDM_ROUTER_RATE_LIMIT_MAX_WAIT_MS`, default 30 s) fails as `rate_limited` while other channels keep working. The Router hot-reloads the registry (debounced, `CCDM_ROUTER_REGISTRY_DEBOUNCE_MS`, default 250 ms, atomic replace included), so guest, channel, and transport changes apply to the next message with no Router or session restart; an invalid registry (malformed JSON, or a schema failure: missing owner `discord_user_id`, `projects` not an object, a project without a `channel_id`, a channel claimed twice or also a root channel, or wrongly typed guest/root lists) keeps the last good table, revokes no session,  `router status` shows the load error beside the last good load time. A registry reload revokes (`revoked`, reason `deregistered`) every connection of a project that no longer has a route, and a project whose registered channel changed moves its webhook (find or create `ccdm-<project>` in the new channel, persist `webhook_id`, issue an assignment change) before its next reply, so replies never land in the old channel. The Router also pushes the moved Session Scope (`scope_changed` event: `project`, `channel_id`, `type`) to every connection of that project, listener and op-only; the client library adopts it only from its authenticated Router connection, after `hello_ok`, for its own project with a channel (a reconnect's `hello_ok` naming another channel counts too), and exposes it as `client.scope`. The Codex bridge then filters inbound messages and reactions by the new channel and moves its active output, typing, queued turns, and queued compaction there; its scoped MCP server targets the Router-granted channel rather than its launch `CHANNEL_ID`; and the Claude channel server's implicit `read_last_x_messages_in_channel` and `export_message_range` read the new channel and it rewrites its reminder capability marker. No session restart is needed.
- Root Codex sessions steer active turns for the same channel and author while preserving the active Discord grant; other channels/authors queue, and failed steering falls back to a fresh scoped turn.
- The Codex bridge forwards allowed users' 👍 and 👎 reactions on its own messages to the active Codex thread.
- The tracked Usage Stats Poster discovers named and legacy Codex Homes, deduplicates shared homes, and falls back from live rate limits to recent session JSONL data.
- The tracked Usage Stats Poster also collects sanitized UTC 10-minute snapshots in a private SQLite history, retains them for 365 days, warns on feature-owned history growth, and posts the original text Usage Report embed per UTC 30-minute slot without any image attachment; any run in a slot posts until the local posts ledger records it, so skipped runs and posts that never reached Discord retry within the slot (a lost reply records the slot to avoid duplicates), and the ledger and advisory lock keep retries idempotent.

For every task, follow this loop:

1. **CONTEXT** — Load the relevant context file(s) from the routing table above. Check `patterns/INDEX.md` for a matching pattern. If one exists, follow it. Narrate what you load: "Loading architecture context..."
