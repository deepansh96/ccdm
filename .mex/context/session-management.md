# Session Management

## Registry

`registry.json` contains `discord_user_id` (the owner), `guild_id`, `root_channels` (the first is the primary root channel), `root_allowed_user_ids`, `category_ids` (guest-managed categories), the Codex account fields, and `projects`. Project records contain path, channel ID, `webhook_id`, tmux `screen_name`, session `type`, PID/session state, `guest_user_ids`, `ws_port` for Codex, and optional account/model overrides. The registry holds no bot or webhook token; the root token stays in root's state `.env` and webhook tokens in private Router state. The Router watches the registry and applies changes to the next message.

Every registry read-modify-write holds one cross-process lock, the `registry.json.lock` directory beside the registry (built under a staging name and renamed into place with an `owner` file naming the holder's pid and a per-acquisition `nonce`; a dead holder's lock is removed only by the one waiter holding its `registry.json.lock.reclaim-<key>` claim after rechecking it is still that dead instance, so a late waiter never displaces a live lock; a live holder is waited for up to `CCDM_REGISTRY_LOCK_TIMEOUT_MS`, default 30 s), rereads the registry, and commits through a unique adjacent temporary file renamed over it with its mode kept. Node writers use `updateRegistry` in `scripts/router/registry.js`; shell and Python writers use `scripts/registry-update.py` (`set-project-fields <registry> <project> '<json>'`, or `update_registry`/`set_project_fields` loaded with `importlib`). Never rewrite the registry in place or outside that lock: an unlocked whole-file rewrite drops a concurrent writer's change (for example a webhook recreation), and truncating in place lets the Router's reload read a partial file.

Never print tokens. Treat missing project `type` as `claude`. Use exact tmux targets (`=<screen_name>`) and expand home paths before comparing them.

## Claude Lifecycle

Use `scripts/start-session.sh <project>`. It rejects duplicate tmux/listener processes and a project without `webhook_id` (pointing at `migrate-to-router.sh`) before any key, launch file, tmux session, or PID, launches Claude through `zsh -ic`, and records PID/session ID. Optional `claude_home` selects `CLAUDE_CONFIG_DIR`; `model` and `claude_effort` set the listener's `--model` and `--effort` flags. Supported effort values are `low`, `medium`, `high`, `xhigh`, and `max`. Missing, null, or empty effort uses the default; other values are rejected before field splitting, MCP config creation, or launch.

Every Claude project runs through the Router, whatever its `transport` field says: Claude has no pool mode and needs no pool bot, and the retired `CCDM_CLAUDE_REMINDER_ADAPTER=1` opt-in changes nothing. `start-session.sh` writes a fresh 0600 launch key at `<router state>/keys/<project>.key` (revoking the previous launch), a secret-free MCP config and settings under `<router state>/launches/<project>/`, and launches `claude --dangerously-load-development-channels server:ccdm` with only the key file path (`CCDM_ROUTER_KEY_FILE`) and the launch's Conversation Reminder context (project, channel, launch ID, reminder state paths) in its environment: no `DISCORD_STATE_DIR`, token, supplementary read-only Discord MCP, or reminder proxy. The `scripts/ccdm-channel-server.js` channel server says hello to the Router, turns Router `message`/`reaction` events into channel notifications with the plugin's attachment metadata (and shows the bot typing on each message, as the plugin does), and forwards `reply` (files, `reply_to` jump link), `react`, `edit_message`, `fetch_messages`, and the supplementary MCP's `read_last_x_messages_in_channel` and `export_message_range` (same arguments and result lines) to Router operations. `download_attachment(chat_id, message_id)` asks the Router for each attachment's signed URL and downloads it itself into the private inbox `<router state>/inbox/<project>/` (0700, files 0600, named `<epoch ms>-<attachment id>.<ext>`), returning the plugin's `downloaded N attachment(s):` lines. Router errors such as `scope_violation` come back to Claude as `<tool> failed: <code> <message>` tool errors. Instead of PATCHing a nickname, the statusline scripts (`_update-nickname.sh`, keyed on `CCDM_ROUTER_KEY_FILE`) write the latest context percentage to a 0600 `<router state>/launches/<project>/context.json` on every render, and the channel server sends it as `context_pct` on each `reply` and `edit_message`, so replies post as `<project>-claude · N%`; a missing or unreadable file omits `context_pct` and the suffix is dropped. Each launch removes the previous launch's `context.json`. The launcher accepts the per-launch development-channel confirmation by sending Enter to the tmux pane, then records the PID only after the channel server reports `hello_ok`; a confirmation that never appears or a failed hello (bounded by `CCDM_CLAUDE_LAUNCH_TIMEOUT_S`, default 60 s) kills the tmux session, removes the key and launch files, and exits non-zero. `stop-session.sh` finds router listeners by that key file path (and, while the project still names a pool `bot_id`, a pre-cutover official-plugin listener by that bot's `DISCORD_STATE_DIR`), removes the key and launch files, and the Router then marks the channel's messages 💤. Plain `/pause`, `/unpause`, `/compact`, `/clear`, and `/restart` from the owner or a channel guest arrive as Router `command` events that the channel server runs itself, never as a Claude turn, acknowledging each like the Codex bridge (a reaction, then a short reply): `/compact` and `/clear` are typed into the project's own tmux pane through `scripts/send-claude-command.sh`, `/pause` holds inbound messages and reactions in memory until `/unpause` delivers them in order, and `/restart` runs `stop-session.sh` then `start-session.sh` for that project only (never root) from a backgrounded subshell that outlives the stopped session, logging to `$TMPDIR/ccdm-restart-<project>.log`; the relaunch writes a new launch key. Conversation Reminders need no opt-in for a Claude launch: the channel server records owner interactions, delivered `reply` receipts (with `conversation_interaction_id` and `conversation_disposition`), input requests, and resumed work through `conversation-reminder-adapter.js`, while the launch settings carry the SessionStart, Stop, StopFailure, and SessionEnd command hooks. After `hello_ok` it writes the capability marker (`transport: "ccdm-channel-server"`), which it removes when it exits or its Router session ends, and every launch clears it first.

For an explicit history-preserving Claude restart, use `scripts/start-session.sh <project> --resume <session_id>` with a canonical session UUID. The launcher requires the transcript `<home>/projects/<project path, each non-alphanumeric character as "-">/<session_id>.jsonl` in the launch's Claude home (`claude_home`, else `CLAUDE_CONFIG_DIR`, else `~/.claude`) and refuses a missing transcript, a malformed ID, or an already running tmux session before any key, launch file, tmux session, or PID. It adds `--resume <session_id>` to the same launch, and a launch that fails the development-channel confirmation or Router hello cleans up and exits non-zero rather than starting fresh. `session_id` in the registry is the Claude session UUID recorded at launch from `<home>/sessions/<pid>.json`; while the session runs, that live file's `sessionId` can move past the recorded one (for example after `/clear`), so it is the fresher source.

Claude `/compact` and `/clear` reach the session as tmux keystrokes typed through `scripts/send-claude-command.sh` by the channel server's command adapter, not as protocol calls.

A Claude Thread Conversation is started only by the Thread Supervisor, through `scripts/start-thread-session.sh <project> <thread_id> --provider claude [--account <alias>] [--model …] [--effort …]`: a fresh `keys/.thread-<thread_id>.key`, the launch directory `launches/<project>/threads/<thread_id>/` (`mcp.json`, `settings.json`, `ready.json`, `bootstrap.json`, `context.json`), tmux `<screen_name>-t-<last 6 of the thread id>` through `zsh -ic` in the project path. `--account` is an alias in the top-level `claude_accounts` map (alias → Claude home), never a path; without it the project's `claude_home`, then the default home applies, and an unknown alias fails the start. The launcher refuses while any process carries that exact key path, cleans up the key, launch directory and tmux session on failure, and prints `{pid, provider_conversation_id, tmux, provider_home}`; the Claude session id goes to the supervisor's store, never the registry. Thread discovery and kills match only that `.thread-<id>.key` path, so project sweeps (exact `<project>.key`) never match a thread session.

A Codex Thread Conversation uses the same launcher with `--provider codex`, the same key, launch directory and tmux names, and needs `CCDM_THREAD_WS_PORT`, the app-server port the Thread Supervisor allocated (base 19000, or `CCDM_THREAD_WS_PORT_BASE`; registry `ws_port`s, ports held by store rows and ports in use are skipped) and recorded on the row. Its Codex Home is `resolve-codex-home.py <registry> <project> --account <alias>`, the thread alias taking the place of the project's `codex_account`; without one the project's own Codex Home applies, and an unknown alias fails the start. tmux runs `codex-bridge.js` from the CCDM checkout through `zsh -ic` with `CHANNEL_ID` set to the thread id, `PROJECT_DIR` the project path, and `CCDM_THREAD_ID`, `CCDM_THREAD_PROVIDER=codex` and `CCDM_THREAD_BOOTSTRAP_FILE`; model and effort fall back to the project's Codex settings. The launcher waits for the bridge's `ready.json` and prints `{pid, provider_conversation_id, tmux, provider_home, ws_port}`, where the conversation id is the Codex thread uuid. It does not strip the Codex Home config: the bridge's own registration of `discord-<thread_id>` runs under the per-Codex-Home lock and verifies after reload that it is the only `discord-*` server loaded, so a project session and its threads sharing one home each keep only their own.

Create a configured Thread Conversation with `/thread <name> [--provider claude|codex] [--account <alias>] [--model <model>] [--effort <effort>] [first message…]` in the project channel (owner or guest; a quoted name may hold spaces), or `scripts/threads.sh create <project> <name> [flags] [message]`, which talks to the running Thread Supervisor over its private 0600 `control.sock` in the supervisor state dir. The account must be an alias in the chosen provider's `claude_accounts` or `codex_accounts`; effort is `low|medium|high|xhigh|max` for Claude and `none|minimal|low|medium|high|xhigh` for Codex. A bad flag or setting creates nothing: `/thread` answers `Thread not created: <reason>` in the channel, and `threads.sh` exits 2 (1 when no supervisor answers). The root bot creates the thread with a one-week archive and posts the settings in it; with a first message the session starts at once with that message as its starter, otherwise on the first owner or guest message.

A Thread Conversation's lifecycle follows Discord. An archive stops its session at once (`stopped/auto-archive`), then the Thread Supervisor polls audit-log action 111 through `thread_archive_actor` for up to 60 s, counting only entries whose changes set `archived` to true (`CCDM_THREAD_ARCHIVE_POLL_WINDOW_S`, every `CCDM_THREAD_ARCHIVE_POLL_INTERVAL_S`, default 5 s): the owner's archive closes it as `closed/owner-archive`, the root bot's as `closed/root-archive`; any other actor, or no entry after successful fetches, stays `stopped/auto-archive`, and a lookup where every fetch was forbidden or failed is `stopped/archive-actor-unknown`, which fails open as an auto-archive. An unarchive, and the repeated `THREAD_CREATE` after a bot unarchive, start nothing. A delete stops the session and drops its row and boot buffers; provider conversation files stay. Stopping kills only the processes carrying that thread's `.thread-<id>.key` path, then its own tmux session and key. An owner or guest message in a `stopped` thread, or only an owner message in a `closed` one, starts it again through the normal boot handoff with `start-thread-session.sh … --resume <provider_conversation_id>` (`claude --resume`, or the bridge's `CODEX_RESUME_THREAD_ID`) in the same home and cwd; a missing Claude transcript or Codex rollout fails the start with a one-line reason (`stopped/start-failed`), never a fresh conversation.

In-thread management commands affect only their own thread, and none reaches a model as a message. `/restart` (owner or guest) stops the thread's session and relaunches it with `--resume` into the same conversation; `/clear` (owner or guest) relaunches it with no `--resume`, a fresh conversation; only the owner's reopens a `closed` thread. `/close` is owner-only (a guest gets a one-line refusal): the Thread Supervisor posts its root-bot acknowledgement first (a post after archiving would unarchive the thread), sets `pending_close`, archives through `thread_update`, stops the session, and leaves `closed/close-command`; an archive event for a row with `pending_close` closes it the same way. A `/restart`, `/clear` or `/close` that arrives while the thread's launcher still runs waits for the launcher to exit. `/compact`, `/pause` and `/unpause` go to the live session: the thread-mode channel server types `/compact` into its own pane (`CCDM_THREAD_TMUX` in its `mcp.json`) and queues events while paused, and a Codex thread's bridge handles them as in a channel. With no live session the supervisor answers `No live session in this thread.` Supervisor answers are root-bot notices.

Live thread sessions are capped per provider by the registry's `thread_session_caps` (`{"claude": 6, "codex": 8}` by default; an invalid value falls back to its default and is listed under `capacity.invalid` in `scripts/thread-supervisor.py status`); Channel Conversations never count. A start at the cap evicts the idle live thread whose last owner message (or creation) is oldest, leaving it `stopped/evicted` with `Paused to free a session slot; reply to resume.` in its thread, so the next owner or guest message resumes it. Idle means its launch dir's `activity.json` shows `turn_running: false` and that owner activity is at least 30 minutes old (`CCDM_THREAD_IDLE_S` overrides it for tests); a missing or unreadable file means busy, and a booting or mid-turn session is never evicted. With no idle session the thread is `queued` with `Queued, N sessions busy.`, keeps its messages buffered, and starts automatically, FIFO per provider, when a stop, close, archive, delete or failed start frees a slot.

While the Thread Supervisor is down, the Router marks an owner or guest message in a thread with no live session 💤. On its own start, each Router reconnect and each Gateway resume (`gateway_resumed`), the supervisor reconciles against Discord: a `booting` or `live` row whose process is gone becomes `stopped/crashed`; `thread_list` (active threads, and archives within 7 days) binds unknown eligible threads under the normal binding rules and classifies archives it missed through the audit-log actor lookup; and a thread starts only when `thread_history` shows its newest owner message is newer than its newest project-webhook message, with the owner and guest messages after that agent reply in its bootstrap, each exactly once. That bootstrap is the only delivery of a 💤-marked message. `crashed`, `start-failed` and `operator` stops never restart automatically.

`/config` in a thread is owner-only (a guest gets a one-line refusal). With no arguments it posts the thread's provider, account alias, model and effort, each marked `(thread)` or `(project)`. `model=<m>` and `effort=<e>` are validated by `/thread`'s rules, saved as overrides, and restart a running session with `--resume` into the same conversation. `provider=` and `account=` (aliases only) post a warning with ✅ on it and store `pending_config`; only the owner's ✅ on that exact message applies the change, clears `provider_conversation_id`, and starts a running session fresh. An invalid value posts `Settings not changed: <reason>`. In a project channel, `/config` reaches only the supervisor and lists the settings new threads inherit; it never changes channel settings.

The Thread Supervisor watches the registry. A project that leaves it has each thread session stopped and its rows set `closed/deregistered`, and a changed `channel_id` sets them `closed/project-moved` (the Router revokes their connections with `project_moved`); neither makes a Discord call. Channel maintenance never touches threads: "restart <project>" restarts the Channel Conversation only unless the request names its threads, and `start-session.sh <project>`, `stop-session.sh <project>`, a channel restart and a project key rotation act on the Channel Conversation only. `stop-session.sh <project> --threads` stops only the project's thread sessions, through the supervisor's control socket (`stop_threads`), as `stopped/operator`, which nothing restarts automatically; with the supervisor down it stops the listeners carrying each thread's `.thread-<id>.key` path (threads found in the store and under `launches/<project>/threads/`), removes their tmux sessions and keys, and marks the rows when no worker holds the store. `--all` stops the channel session and then the threads. Guests are read from the registry on every message, so a revoked guest can no longer drive or resume a thread.

A project's Channel Conversation, Claude or Codex, can hand a side task off with its `create_thread` tool (`name`, optional `provider`, `account`, `model`, `effort`, `first_message`): the same validation and creation flow in its own channel only, returning the new thread's id, an op error (`invalid: <reason>`) that creates nothing, or `supervisor_unavailable` when no Thread Supervisor runs. Thread sessions and root have no such tool.

## Codex Lifecycle

Use `scripts/start-codex-session.sh <project>`. It validates the target project's named `codex_account` or legacy `codex_home` selector and the applicable top-level `codex_accounts`/`default_codex_account` or legacy selector through the shared resolver before stale MCP cleanup, tmux creation, or PID recording, refuses a project without `webhook_id` (after the duplicate checks, still before any runtime change), then passes the resolved channel, guild, bot, allowlist, home, model, and WebSocket configuration to `codex-bridge.js`, which owns `codex app-server`. Project precedence is project named/raw selector, top-level default named/raw selector, then `~/.codex`; a same-scope named/raw conflict or unknown alias fails before lifecycle mutation. The root bridge uses the same resolver for `ROOT_CODEX_HOME`, then the top-level named/raw selector, ambient `CODEX_HOME`, then `~/.codex`, and validates the selection before tearing down `root_agent`. Model overrides use `codex_model`, `codex_reasoning_effort`, and `codex_service_tier`.

Bridges sharing a Codex Home register their Discord MCP server under a lock on that home's `config.toml` (`config.toml.lock`, the registry lock protocol): `codex-bridge.js` deletes every other `discord-*` server, loaded or configured, writes its own and reloads while holding it, and `start-codex-session.sh` takes the same lock to strip `[mcp_servers.discord-*]` entries. After the reload the bridge refuses to start, with a one-line reason and before any Router hello, if its app-server still loads a foreign `discord-*` server. The entries hold the Router key path and the scope token, never a Discord credential.

Every Codex project runs through the Router, whatever its `transport` field says: Codex has no pool mode and needs no pool bot. `start-codex-session.sh` writes a fresh 0600 launch key at `<router state>/keys/<project>.key` (revoking the previous launch) and launches `codex-bridge.js` in Router mode with only the key file path (`CCDM_ROUTER_KEY_FILE`), `CCDM_CODEX_PROJECT`, and `CCDM_ROUTER_STATE_DIR` in its environment: no `BOT_TOKEN`, bot identity, or root bot app ID. The bridge's Router transport (`scripts/codex-bridge-transport.js`) turns Router `message`, `reaction`, and `command` events (a command arrives as its plain `/command` text) into the bridge's own shapes and sends replies, reactions, and typing as Router operations, so steering, pause, bootstrap, voice, and plain `/pause`, `/unpause`, `/compact`, `/clear`, and project-only `/restart` keep their pre-Router behavior. Each attachment URL is resolved through the Router's `download_attachment` (which re-signs a URL that expired while the message was queued) before the bridge fetches, transcribes, or saves it. 👍/👎 reactions are forwarded only on the project's own messages: the Router's reaction event carries the reacted message's `message_webhook_id` (fetching a partial message first) and `message_content`, and the bridge matches that against the project's current registry `webhook_id`, never a bot user ID. The bridge's scoped `discord-<channel>` MCP server gets the same key file path instead of a token and forwards its tools to Router operations over an op-only connection (`listener: false`), which receives no events and never replaces the bridge as the project's listener; the `scope_token` checks stay. Instead of PATCHing a nickname, the bridge writes its token-usage percentage to a 0600 `<router state>/launches/<project>/context.json`, and both the bridge and the MCP server send it as `context_pct`, so replies post as `<project>-codex · N%`. The bridge writes its startup outcome to `<router state>/launches/<project>/ready.json` once Codex is bootstrapped and the Router hello is answered; the launcher records the PID only on `hello_ok`, and a failed hello or a bridge that never reports (bounded by `CCDM_CODEX_LAUNCH_TIMEOUT_S`, default 120 s) kills the tmux session and its listeners, removes the key and launch files, and exits non-zero. Router Codex reminder events go through the unchanged adapter calls, which resolve a project to the identity `router:<webhook_id>`; root sends its reminders (see `docs/conversation-reminders.md`).

After a Codex CLI upgrade, stop every long-lived CCDM Codex session before starting any replacement, then restart the root Codex bridge. Running app-server processes keep their original runtime version.

A ChatGPT-account home can only run the models listed in that home's `models_cache.json`, which the app-server refreshes at startup against the running CLI's client version. Requesting anything else fails at the backend with `The '<model>' model is not supported when using Codex with a ChatGPT account.` That message also appears when the installed CLI is simply older than the model's release: `gpt-6-sol` was rejected on 0.153.4 and worked immediately after `npm install -g @openai/codex@latest` (0.155.1), which then listed `gpt-6-sol`/`gpt-6-luna` in the refreshed catalog. Confirm the slug against a live home's catalog before writing `codex_model` rather than guessing from a display name.

MiMo API accounts use the same named-account selection and launch path. `scripts/setup-codex-mimo.py` creates an external home with a private `api-key`, provider auth command, and Xiaomi model catalog; it does not mutate registry selectors. Add the home as a `codex_accounts` alias and select it only on the intended project. Omit incompatible GPT model/service-tier overrides. The provider reads credentials from its home, so no MiMo key is passed through tmux command arguments. `--rotate-key` replaces only the private credential; restart affected sessions afterward. MiMo API quota reporting is outside the ChatGPT usage dashboard's scope.

DeepSeek Flash homes follow the same selection and authentication flow through `scripts/setup-codex-deepseek.py`. Its catalog uses standard Responses and shell-command tools, not MiMo's Responses-lite/code-mode metadata. The helper extracts the vendor's literal catalog without executing its installer; only `deepseek-flash` is selected (V4.1 Flash as of 2026-09-22). Image support does not itself configure Computer Use tools, and usage reporting shows account-wide DeepSeek balance separately from local Codex token totals.

Root multi-channel sessions accept steering only from the active channel and author, reusing the active turn's Discord scope token so in-flight tool calls stay valid. Messages from other channels/authors queue until the turn finishes. Failed steering queues the original message with its own scope for the next turn. Steering was verified live with DeepSeek Flash through app-server; this behavior is provider-independent.

Codex channels handle `/compact`, `/clear`, and `/restart` directly in the bridge.

For an explicit history-preserving restart, use `scripts/start-codex-session.sh <project> --resume <thread_uuid>`. This resumes only at startup; `/clear` still creates a fresh thread. A resume launch requires the fresh Discord instruction request to be accepted and waits up to 60 seconds for listener readiness before reporting success. Failure or timeout returns nonzero and uses the common stop script to clean up listeners and registry runtime state instead of silently creating a new conversation. To change accounts while preserving history, identify and verify the current rollout's thread ID and project directory, stop the old session through the common stop script, copy that rollout into the target home's corresponding `sessions/` path without overwriting an existing file, update only the project's account selector, and start with `--resume`. Keep the original rollout and account selection for recovery. Credentials are never copied. Verify the resumed thread ID, selected process home, and channel listener. In-flight processes do not survive the restart.

## Stop Invariant

`scripts/stop-session.sh <project>` is the common teardown path for the Channel Conversation (thread sessions keep running; add `--threads` or `--all` for them): kill the recorded process tree, kill the exact tmux session, sweep listener processes by assignment identity, then clear `pid` and `session_id`. Do not replace this with only `tmux kill-session`; orphan listeners have caused duplicate processing.

## Registration

Registration creates or resolves the channel with root's REST credentials, writes the entry (`path`, `screen_name`, `channel_id`, `type`), runs `node scripts/router.js ensure-webhook <project>`, and starts the session; there is no bot to assign or rename. Deregistration stops the session (`scripts/stop-session.sh <project> --all`, which also stops its Thread Conversations), runs `node scripts/router.js delete-webhook <project>`, and removes the entry; the Thread Supervisor then sets the project's threads `closed/deregistered`. Both then run `scripts/conversation-reminder-service.py assignment-changed --project <project>`, which retires the old reminder generation, deletes its recorded reminders at once (reporting any it cannot delete as inaccessible), and writes a fresh `assignment_generation` for a registered project; see `docs/conversation-reminders.md` and `patterns/register-project.md`.

## Router Cutover And Retirement

These executables moved a Bot Pool install onto the Router and remain for registries that still carry pool fields. The cutover order is fixed:

1. Stop every pool session with `scripts/stop-session.sh <project>`; while a project keeps its pool `bot_id`, the stop also sweeps that bot's leftover official-plugin listener.
2. Move root's configuration: `node scripts/router.js migrate-root-config`, `scripts/install-router-service.sh`, `node scripts/router.js status`, then restart root.
3. Migrate each project with `scripts/migrate-to-router.sh <project>`. Launchers refuse a project without `webhook_id`, so this is how an unmigrated project gets back online.
4. Retire the pool with `scripts/retire-pool.sh` (dry run), then `--apply`.

`scripts/migrate-to-router.sh <project>` (orchestrated by `scripts/router/migrate.js`) records one project on the Router: preflight (Router reachable with its gateway ready, project registered and not already on the Router, no missing root permissions in its channel from `status` with `args.project`), then `stop-session.sh`, `ensure-webhook`, `transport: "router"` (waiting until the Router has reloaded it), `assignment-changed`, the provider's launcher, and verification (`router status` shows the project's session in its channel, and `router.js probe <project>` posts one notice through the webhook and requires Discord's returned `webhook_id` to match the registry). A preflight failure touches nothing; a failure from the stop onward stops the session, restores the previous registry state, reissues `assignment-changed` if it ran, and starts the provider's launcher again (which refuses if the failure came before `ensure-webhook` recorded a webhook), then exits non-zero naming the failed step. `--rollback <project>` refuses at preflight: no pool bot remains to return to.

`migrate-to-router.sh --resume <project>` resolves the conversation to keep after preflight and before the stop (which clears `pid` and `session_id`), printing `resume: <id> (<source>)` or `resume: skipped — <reason>` (`scripts/router/resume.js`). Claude: the live `<home>/sessions/<pid>.json` `sessionId` when the recorded PID is alive and its `cwd` matches, else the registry `session_id`; the transcript must exist in the project's Claude home. Codex: the launchers record `session_id: null` (the bridge only logs `Codex thread started: <id>`), so a UUID `session_id` is used if present, else the newest rollout under the resolved Codex home's `sessions/` whose `session_meta` has `originator: "codex-discord-bridge"`, a string (non-subagent) `source`, and the project directory as `cwd`; a directory another Codex project shares, or the CCDM checkout (root's bridge threads), is skipped as ambiguous. The start step, and a rollback's start, run the launcher with `--resume <id>`; a launcher failure there prints `resume: skipped — the launcher could not resume …; starting fresh` and starts fresh. No id, a missing transcript/rollout, or a failed resume never fails the migration by itself. Cutover step 1 clears `session_id`, so resume works for projects migrated while still running or whose live session file survives.

`scripts/retire-pool.sh` (orchestrated by `scripts/router/retire-pool.js`) retires the Bot Pool. It refuses, naming the offenders, while any project still carrying a pool marker (`bot_id`, `bot_display_name`, or a pool entry's `assigned_to`) lacks `transport: "router"`; projects registered after the cutover (no `transport`) and projects an interrupted `--apply` already stripped pass. It is a dry run (`would <action>` lines, no changes) unless given `--apply`, which prints `done: <action>` as it removes every pool entry's guild membership by `app_id` with the root token (a 404 counts as removed), moves each existing `state_dir` (a leading `~` expands to the home directory) into `<backup>/state/<bot id>` (0700), deletes the obsolete `project-bot` role, copies the registry to `<backup>/registry.json` (0600, never overwritten), and strips `pool`, `max_pool_size`, `project_bot_role_id`, `bot_id`, `bot_display_name`, and `transport`, each strip a separate locked registry write. The backup defaults to `~/.local/state/ccdm/pool-retirement` (`CCDM_POOL_BACKUP_DIR` overrides it). A `state_dir` it cannot move (none named, not absolute, or missing with no earlier backup) is listed as `would skip`/`skipped: <action>`, and `--apply` finishes the rest, then exits 2 with a summary of the skipped items instead of reporting success. It never deletes bot applications; a rerun after an interruption finishes the remaining strips, and once nothing is left to strip a rerun is a no-op.

## Codex Startup

Codex startup enumerates all MCP status pages (`data`, with legacy `servers`/`items` compatibility) and waits for the scoped Discord `reply` tool before creating/resuming the thread. `CODEX_MCP_READY_TIMEOUT_MS` defaults to 30000. Bootstrap is configuration-only and explicitly forbids tools or Discord writes. It stays tracked until completion; `CODEX_BOOTSTRAP_TIMEOUT_MS` defaults to 60000, after which the bridge pauses, requests interruption, and fails startup rather than declaring a still-running turn idle. Failed bootstrap completions also fail startup. Discord transport must use exposed MCP tools, never shell-launched replacements.
