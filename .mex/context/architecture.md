# Architecture

## System Overview
```text
Discord (one bot: root) <-> Router (scripts/router.js, holds the only token; a service on both OSes)
  <-> private local socket (Unix socket on macOS, named pipe on Windows; NDJSON, per-launch keys, Session Scope checks)
    -> root: ccdm-channel-server.js (root role) or codex-bridge.js (root mode)
         root channels + bot mentions; start/stop/guest/registration scripts
    -> Claude project: ccdm-channel-server.js -> Claude Code in project directory
    -> Codex project: codex-bridge.js -> codex app-server in project directory
    -> Gemini project: gemini-bridge.js -> agy acp (ACP over stdio) in project directory
    -> Conversation Reminder observer (read-only)
    -> Thread Conversation (thread role, one per live thread): ccdm start-thread-session ->
         ccdm-channel-server.js (thread mode) -> Claude Code, codex-bridge.js (thread mode) -> codex app-server,
         or gemini-bridge.js (thread mode) -> agy acp
    -> Thread Supervisor link (supervisor role) <-> NDJSON stdio <-> Python worker
  replies -> project webhook ccdm-<project> as "<project>-<type> · N%" (in a thread: ?thread_id=, named for the thread's provider)
```

The root agent coordinates lifecycle and access. Each project session works only in its registered directory and, through the Router, only in its registered channel (its Session Scope).

Every session runs in a session host: tmux on macOS, `ccdm-host` (`scripts/ccdm-host.js`, ConPTY) on Windows. `scripts/ccdm` is the one command line for both. Its lifecycle subcommands reach the host through one session-host API, so the same command works on either OS. Where this file says "tmux session", read "hosted session" on Windows.

## Key Components
- **`registry.json`** - source of truth for the owner, root channels and allowed users, project channels and `webhook_id`s, guests, session names, account homes, and runtime PIDs; local and untracked. It holds no bot or webhook token.
- **Session commands** - `scripts/ccdm start-session`, `scripts/ccdm start-codex-session`, `scripts/ccdm start-gemini-session`, `scripts/ccdm stop-session` and `scripts/ccdm restart-session` enforce one listener per assignment and maintain registry runtime state. `scripts/ccdm list`, `status`, `session` and `context report` read and drive sessions for root. The shell scripts with the same names are shims that run them.
- **`scripts/gemini-bridge.js`** - connects Discord to a Gemini session in the Google Antigravity CLI: it runs `agy acp --dangerously-skip-permissions` in the project directory and speaks the Agent Client Protocol (JSON-RPC over stdio) to it. It reuses the Router transport seam (`codex-bridge-transport.js`) and the scoped `discord-mcp-server.js`, which it attaches to its one agy session through `session/new` `mcpServers` (no agy config file is written, so no config lock), and appends the Discord transport instruction to the session's system prompt (`_meta.antigravity.systemPrompt.append`), so it needs no bootstrap turn. ACP cannot steer a running prompt, so mid-turn messages queue with ⏳ and go into the next turn together; tool permission requests are approved; a turn that ends with text but no successful `reply` (tracked by the tool call's `completed`/`failed` status) posts the text. Agent-started turns (`request`, `reply`, `notice`) run with no reminder context (recording no MCP or text-fallback reply receipts and emitting no `turn_completed`); owner input queues behind them and starts an ordinary turn. Model and thinking level are ACP config options (`session/set_config_option` `model`, `thought_level`).
- **Claude reminder events** - every Claude session's `ccdm-channel-server.js` records owner interactions and reply receipts itself; command hooks and the shared durable receiver record lifecycle events. Live reminder arming comes from these adapter receipts (webhook-ID matching is used only for history discovery), and a turn started by delivering an Agent Message (`request`, `reply`, or `notice`) records no reply receipts or turn completions until owner input joins mid-turn. The foreground service owns reminder delivery, bounded history discovery, restart/reconnect reconciliation, and globally spaced catch-up; `enable` opts in only when both provider adapters are installed.
- **Conversation Reminder service** - `conversation-reminder-service.py run` observes every project channel as the Router's read-only `observer` client, with no Gateway login of its own and whatever the registry `transport` says. It identifies each project as `router:<webhook_id>`, sends every reminder, acknowledgment, and cleanup delete as root over REST (including deletes left by v7 `pool:` history rows), and detects agent replies in history discovery by the project's `webhook_id` (classifying `-# ⇄ Agent ` records as `other`). It runs in the foreground or, on macOS, under the opt-in `com.discord.conversation-reminders` LaunchAgent. Both launches share one worker lock and the same reconciliation, independently of project and root coding sessions.
  - macOS: `install-conversation-reminder-service.sh` installs that LaunchAgent.
  - Windows: `scripts/ccdm install-service reminders` installs the opt-in task `\CCDM\Reminders`, which runs the same worker through the service host. `scripts/ccdm reminders run` runs it in the foreground, and `scripts/ccdm reminders` has the other operator commands.
- **`scripts/codex-bridge.js`** - connects Discord to `codex app-server`, injects mid-turn messages, handles attachments/audio, and exposes channel-scoped MCP tools. Its Discord I/O goes through the transport seam in `codex-bridge-transport.js` (events in, operations out); the Router transport is the only implementation, so Codex has no pool mode and the bridge holds no Discord token. Agent-started turns (`request`, `reply`, `notice`) run with no reminder context (recording no MCP or text-fallback reply receipts and emitting no `turn_completed`) unless owner input joins the turn through `turn/steer`, which creates the reminder context and restores normal arming.
- **Discord range export** - `export-discord-range.js` paginates an inclusive message range into a temporary transcript; sessions reach it only through the Router's `export_message_range` operation (the Codex bridge MCP and the Claude channel server).
- **`scripts/guest-access.js`** - creates and synchronizes project-scoped guest roles and channel overrides and the registry's `guest_user_ids`, which the Router reloads live.
- **`scripts/usage-stats-poster.py`** - reads the ignored poster config, gathers the default and valid extra Claude OAuth accounts through the Keychain and Anthropic OAuth boundaries, discovers and deduplicates compatible named/legacy Codex Homes, writes sanitized UTC-slot snapshots to a private SQLite history with advisory locking/retention, and preserves the manual combined embed surface. Automated LaunchAgent runs reuse that bounded text summary and post the original text Usage Report embed once per UTC 30-minute slot through a local ledger, with no image rendering or attachment. Configured DeepSeek homes are reported from their private key instead of the Codex rate-limit request: the poster validates the documented account-wide `GET /user/balance` response (USD/CNY only, all amounts required and preserved exactly) and pairs it with this machine's local DeepSeek token totals in a compact `deepseek (API)` text block that uses an optional `deepseek_balance_references` display budget for an inline used-balance bar with used and remaining percentages and no quota card, while a DeepSeek-backed root Codex session still runs through the Codex app-server.
- **`scripts/usage-dashboard-renderer.py`** - credential-free Pillow renderer for the trend-first PNG; retained for back-compat but no longer invoked by the posting workflow. The text-only poster installer does not require Pillow.
- **Router** - `scripts/router.js` (modules in `scripts/router/`, including `scripts/router/agent-messages/` for Agent Messages, its shared `-# ⇄ Agent ` record formatter/poster, and its private append-only `agent-messages.jsonl` ledger — the Router's one durable store, a deliberate exception to ADR 0005 recorded in ADR 0009, leaving Session Scope unchanged; startup recovery resumes partial multi-chunk posts via `post_chunk`, overdue unposted requests before expiry, and missing outcome marks/deliveries under a bounded gateway wait `CCDM_ROUTER_AGENT_MESSAGE_READY_WAIT_MS` default 2 s) holds the root token and one discord.js gateway, classifies inbound events for every registered project (whatever its `transport`), and serves sessions over a private local socket (a Unix socket in `~/.local/state/ccdm/router/` on macOS, a named pipe that admits only the owner's user on Windows; NDJSON, keyed `hello` with additive `capabilities` and launch-key fingerprints). Operations dispatch through `scripts/router/ops/`, one module per family, with Session Scope checked before any op runs (and `agent_request`/`agent_reply`/`agent_targets`/`agent_message_ack` acting on the authenticated `project`/`thread` conversation with no `channel_id`); `reply` executes the project webhook (multipart files, a `↪ [jump](…)` first line for `reply_to`, and 2000-character chunks) and refuses text or any split chunk matching `looksLikeAgentMessageRecord` (`-# ⇄ Agent ` or look-alike `-#` + 1–3 symbols + `Agent` subtext headers, after trimming leading whitespace); `edit_message` edits only the project's own non-record webhook messages (also refusing `looksLikeAgentMessageRecord` new text and editing any chunk of an exact `isAgentMessageRecord`), `react` acts as the bot while refusing adding or removing ✅/⚠️ (including `⚠` without VS16) on any `isAgentMessageRecord` chunk (`invalid_args`), and `typing` acts as the bot. Session-side Agent Message logic (PRD trust note, label/turn formatting, expiry check, error-isolated delivery dedupe/ack/chaining, idempotent retries, and canonical MCP tool schemas) is shared in `scripts/agent-messages-session.js` across `ccdm-channel-server.js`, `discord-mcp-server.js`, `codex-bridge.js`, and `gemini-bridge.js` (`/clear` in Codex and Gemini preserves acknowledged queued Agent Messages while dropping ordinary queued owner messages and expired requests). Reads (`fetch_messages`, `read_last_x_messages_in_channel`, `export_message_range`) use the bot token, with large reads and exports written to private temporary files; `export_message_range` reuses `scripts/export-discord-range.js`. `download_attachment` returns a signed CDN URL for the session to fetch, from the cached event while fresh or by re-fetching the message. Every `message_id` target is fetched from the session's channel first; anything else is a logged `scope_violation`. `scripts/router/client.js` is the shared client library; it reconnects with capped backoff and fails fast with `router_unavailable` while disconnected. A thread hello waits up to 60 s for a restarted Router's gateway before its thread check, and a refused reconnect hello ends the client except `not_ready`, which it retries. The Router watches `keys/` and revokes any session whose key was replaced, and watches the registry directory to rebuild the routing table after a debounced change (`CCDM_ROUTER_REGISTRY_DEBOUNCE_MS`, default 250 ms); a registry that fails to load keeps the last good table and is reported by `router status`. When a reload moves a connected project's channel, the Router pushes a `scope_changed` event (the new Session Scope) to each of that project's connections; `client.js` validates and adopts it as `client.scope`, and the Codex bridge, its scoped MCP server, and the Claude channel server retarget their inbound filter and implicit tool channel. All Router REST goes through `scripts/router/discord-rest.js`, which queues requests per route bucket, honors bucket headers, `Retry-After`, and the global limit, and fails a request still unsendable after the wait bound (`CCDM_ROUTER_RATE_LIMIT_MAX_WAIT_MS`, default 30 s; `CCDM_ROUTER_RATE_LIMIT_FALLBACK_MS`, default 1 s, when a 429 carries no delay) with the typed `rate_limited` code; repeated `edit_message` calls to one message coalesce to the latest content while an edit is queued or in flight. The Conversation Reminder observer connects with `role: "observer"` and the key in `keys/.observer.key`. It receives every router project-channel message, including webhook and bot messages, plus reactions, and may perform no operation. An owner `/close` goes only to it. Root connects with `role: "root"` and the key in `keys/.root.key`: it receives owner and `root_allowed_user_ids` messages in the registry's `root_channels`, plus the owner's bot mentions and native replies to root-bot messages in router project channels (those never reach the project; a guest's mention reaches no one). Root may target root channels and any registered channel; its `reply` posts as the bot with native replies, and its `edit_message` edits only the bot's own messages. `scripts/ccdm restart-root` runs root Claude as this client: `ccdm-channel-server.js` with `CCDM_ROUTER_ROLE=root`, launched with root's fresh key and no Discord token, and the launch succeeds only after root's `hello_ok`. `scripts/ccdm restart-root --provider codex` runs root Codex as the same client (not on Windows yet): `codex-bridge.js` in root mode (`CCDM_ROUTER_ROLE=root`, root channels and allowed users from the registry), whose scoped MCP server acts as root over an op-only (`listener: false`) root connection. Both root modes arm `scripts/router/emergency.js` when their Router connection drops: after `CCDM_ROOT_FALLBACK_AFTER_MS` (default 120000) without the Router, root logs in directly with the root token, hears only root channels from the owner and `root_allowed_user_ids` (never project channels, mentions included), and posts a one-line notice in the primary root channel; the Router client's `beforeHello` hook closes that direct client before root's next hello. Root admin scripts keep reading the root token from root's Discord state directory. `router.js migrate-root-config` copies root's no-mention `access.json` groups and allowlisted users into the registry once, leaving `access.json` untouched. `router.js serve` takes `router.lock` in the state directory before anything else, so a second foreground or supervised Router exits non-zero without touching the running one; a lock whose pid is dead is reclaimed. The Router runs as a service, installed only after the read-only `router.js preflight` (Node, registry, root token, socket directory ownership and privacy) passes.
  - macOS: `install-router-service.sh` supervises it as the `com.ccdm.router` LaunchAgent: the rendered plist holds only paths with private logs in the state directory and relaunches only after an unsuccessful exit, and a failed replacement load restores the prior plist and loaded service.
  - Windows: `scripts/ccdm install-service router` installs it as the per-user scheduled task `\CCDM\Router`, run through `scripts/win/service-host.js`, which restarts it after a failure with a growing delay and logs to `~/.local/state/ccdm/services/router.log` and `router.err`.
- **Thread Supervisor** - `scripts/thread-supervisor.py run` is the foreground worker (`status` reports it); on macOS the `com.ccdm.thread-supervisor` LaunchAgent supervises it, running `run --supervised`, after the read-only `preflight` (interpreters, Router reachable, registry owner and guild, store), and `enable`/`disable` toggle a `disabled` marker in the state dir that only the supervised worker honours; its modules live in `scripts/thread_supervisor/`, one per concern, with Router events dispatched through a thin table in `dispatch.py`. The worker holds `worker.lock` and a private SQLite store (schema v3, `threads`, `creation_requests`, `boot_buffers`; a v1 or v2 store migrates after a private backup) in `~/.local/state/ccdm/thread-supervisor/`, writes a fresh `keys/.supervisor.key` in the Router state on each start, and spawns `scripts/thread-supervisor-link.js`, the Node link that owns the single `supervisor` Router connection through `client.js` and relays events and op calls as NDJSON over stdio. It has no Discord credential: every Discord action is a Router op. It binds owner-, guest- and requested bot-created threads on `thread_create`. `boot.py` starts a bound thread's Claude session on its first owner or guest message through the `scripts/ccdm start-thread-session` launcher (in a background thread whose exit returns to the event loop as an internal frame), buffers boot-time messages, and on `thread_session_live` writes the bootstrap the thread-mode channel server (`ccdm-channel-server.js` with `CCDM_THREAD_ID`) waits for before delivering live events. `lifecycle.py` handles `thread_update` archives (only an archive by `/close` or the operator's thread `close` command stands; any other is reverted through `thread_update`, its actor logged from one audit-log read, and an idle live session stopped as `stopped/auto-archive`) and `thread_delete`; `turns.py` tracks whose turn it is from each live session's `activity.json` and the supervisor's own message events, and shows it as root's reaction on the latest input (⏳, then ✅ or ⚠️): adapters flag agent-started turns (`turn_agent_started`, `last_turn_agent_started`) and record non-agent turn ends separately (`last_ordinary_turn_end_at`, `last_ordinary_turn_outcome`), clearing the flag when owner input joins the turn, so `turns.py` ignores agent-started turn ends without missing an owner turn that ends with a held Agent Message behind it, and ignores `-# ⇄ Agent ` records; handlers set the wanted mark, and the worker loop syncs it to Discord through `thread_react` with a per-thread backoff; a stopped or owner-reopened closed thread resumes its provider conversation with `--resume`. `commands.py` answers in-thread `thread_command`s (`/restart`, `/clear`, `/close`, and `/compact`/`/pause`/`/unpause` with no live session), deferring one that arrives mid-launch until the launcher exits. `model_info.py` answers `/model` (owner or guest) in threads and project channels with the provider, model, thinking level and account/home, each from the thread override, the project entry or the provider home's `config.toml`/`settings.json`; in root channels the Router hands `/model` to root as a `command`, and root's bridge or channel server answers it from its own launch through `scripts/model-info.js`, with no turn. `config.py` answers `/config` in threads and project channels and applies a pending provider or account change on the owner's ✅ `thread_reaction`. `capacity.py` admits every start against the registry's per-provider `thread_session_caps` (default Claude 6, Codex 8; only `booting`/`live` rows count): at the cap it evicts the idle live session with the oldest owner activity, read from its launch dir's `activity.json` (written by the thread channel server, its UserPromptSubmit/Stop/StopFailure hooks through `thread-activity.js`, or the thread-mode bridge; it also holds the turn outcome, whether the turn replied, and the paused flag), or else queues the row; after every dispatched event the queue drains FIFO per provider. `reconcile.py` runs on every Router connection (worker start and link reconnect) and on `gateway_resumed`: dead `booting`/`live` rows become `stopped/crashed`, `thread_list` binds missed threads and unarchives every archived thread whose row is not closed, and `thread_history` starts only threads whose newest owner message is newer than their newest project-webhook message.
  - macOS: `scripts/install-thread-supervisor.sh` installs the LaunchAgent, and `scripts/threads.sh` is the operator's thread command.
  - Windows: `scripts/ccdm install-service thread-supervisor` installs the task `\CCDM\ThreadSupervisor`, which runs `run --supervised` through the service host after the same `preflight`. `scripts/ccdm threads` is the operator's thread command, and thread sessions live in the session host, so they outlive the task.
- **Root emergency operations and request deadlines** - while `scripts/router/emergency.js` is engaged, root's requester sends `reply`, `react`, `typing`, and `edit_message` directly to Discord by running the Router's own root operations with the root token, limited to root channels (edits to the bot's own messages); everything else still goes to the Router and fails as `router_unavailable`. Release drops the direct path before the direct client closes and before root's next hello. Root Codex's separate MCP server follows the bridge's engagement marker (a file in root's launch directory holding the bridge's pid) and builds its own direct dispatcher. Separately, `client.js` sends each request's `deadline_at` (10 s by default; longer per-op budgets for large reads and exports from `deadlines.js`), `server.js` runs the operation under it, and `discord-rest.js` fails a queued or rate-limited call past that deadline as `timeout` before sending.
- **Cutover and retirement** - two macOS scripts remain for registries that still carry Bot Pool fields; the ordered procedure is in `context/session-management.md`. A Windows install starts on the Router and never needs them.
  - macOS: `scripts/migrate-to-router.sh` (one verified, self-rolling-back project cutover) and `scripts/retire-pool.sh` (dry-run by default; `--apply` removes pool bot members, backs up their state, deletes the `project-bot` role, and strips pool fields).
- **Registry lock** - every `registry.json` read-modify-write (Node `updateRegistry`, shell/Python `scripts/registry-update.py`) holds the `registry.json.lock` directory and commits by atomic rename with the file's mode kept, so the Router's watcher only sees whole files and no writer loses another's change.
- **E2E harness** - Node's built-in test runner plus fixture binaries and local fakes; default tests never contact Discord or agent services.

## External Dependencies
- `Discord API / discord.js` - the Router's one gateway connection and REST (webhooks, messages, reactions), plus root admin REST for channels, roles, invites, and guest permission overrides. Isolation is the Router's Session Scope, not Discord permissions.
- `Claude Code` - runs Claude project and root sessions with the CCDM development channel (`server:ccdm`), never the official Discord plugin.
- `Codex CLI/app-server` - runs Codex project sessions; the bridge registers a scoped Discord MCP server dynamically.
- `Google Antigravity CLI (agy)` - runs Gemini project and thread sessions through `agy acp` (installed in `~/.local/bin` on macOS, `%LOCALAPPDATA%\agy\bin` on Windows); signed in once with Google OAuth per home, and holds its conversations in `<home>/.gemini/antigravity-cli`; each `gemini_accounts` alias is another home with its own sign-in, which agy runs under as `HOME` (macOS and Linux; Windows refuses a Gemini account whose home is not the user's own, since agy there does not take its account from `HOME`). On macOS each extra home needs its own keychain, unlocked at login; agy saves tokens through `/usr/bin/security`, which otherwise pops "Keychain Not Found" on each refresh (README, Gemini sessions).
- `tmux` (macOS) or `ccdm-host` (Windows) - owns long-running local sessions and provides the Claude slash-command relay boundary.
- `macOS Keychain / local auth files` - store agent credentials; never copy their contents into tracked files.

## What Does NOT Exist Here
- No web application; durable configuration is JSON and the Usage Stats feature's private SQLite history is local state only. The history writer never traverses or deletes Claude/Codex source logs.
- No daemon supervisor for project sessions; they must be started again after a reboot. Only background services are supervised: on macOS the Router, reminder service, Thread Supervisor and usage poster have LaunchAgents, and on Windows the Router, `ccdm-host` and the collect-only usage poster have scheduled tasks.
- No remote-host orchestration; remote setup commands are handed to the user.
- No real external calls in the default E2E suite; live smoke tests require `CCDM_LIVE_E2E=1`.
