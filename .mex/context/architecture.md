# Architecture

## System Overview
```text
Discord (one bot: root) <-> Router (scripts/router.js, holds the only token, launchd com.ccdm.router)
  <-> private Unix socket (NDJSON, per-launch keys, Session Scope checks)
    -> root: ccdm-channel-server.js (root role) or codex-bridge.js (root mode)
         root channels + bot mentions; start/stop/guest/registration scripts
    -> Claude project: ccdm-channel-server.js -> Claude Code in project directory
    -> Codex project: codex-bridge.js -> codex app-server in project directory
    -> Conversation Reminder observer (read-only)
    -> Thread Supervisor link (supervisor role) <-> NDJSON stdio <-> Python worker
  replies -> project webhook ccdm-<project> as "<project>-<type> · N%"
```

The root agent coordinates lifecycle and access. Each project session works only in its registered directory and, through the Router, only in its registered channel (its Session Scope).

## Key Components
- **`registry.json`** - source of truth for the owner, root channels and allowed users, project channels and `webhook_id`s, guests, tmux names, account homes, and runtime PIDs; local and untracked. It holds no bot or webhook token.
- **Session scripts** - `start-session.sh`, `start-codex-session.sh`, and `stop-session.sh` enforce one listener per assignment and maintain registry runtime state.
- **Claude reminder events** - every Claude session's `ccdm-channel-server.js` records owner interactions and reply receipts itself; command hooks and the shared durable receiver record lifecycle events. The foreground service owns reminder delivery, bounded history discovery, restart/reconnect reconciliation, and globally spaced catch-up; `enable` opts in only when both provider adapters are installed.
- **Conversation Reminder service** - `conversation-reminder-service.py run` observes every project channel as the Router's read-only `observer` client, with no Gateway login of its own and whatever the registry `transport` says. It identifies each project as `router:<webhook_id>`, sends every reminder, acknowledgment, and cleanup delete as root over REST (including deletes left by v7 `pool:` history rows), and detects agent replies by the project's `webhook_id`. It runs in the foreground or under the opt-in `com.discord.conversation-reminders` LaunchAgent from `install-conversation-reminder-service.sh`. Both launches share one worker lock and the same reconciliation, independently of project and root coding sessions.
- **`scripts/codex-bridge.js`** - connects Discord to `codex app-server`, injects mid-turn messages, handles attachments/audio, and exposes channel-scoped MCP tools. Its Discord I/O goes through the transport seam in `codex-bridge-transport.js` (events in, operations out); the Router transport is the only implementation, so Codex has no pool mode and the bridge holds no Discord token.
- **Discord range export** - `export-discord-range.js` paginates an inclusive message range into a temporary transcript; sessions reach it only through the Router's `export_message_range` operation (the Codex bridge MCP and the Claude channel server).
- **`scripts/guest-access.js`** - creates and synchronizes project-scoped guest roles and channel overrides and the registry's `guest_user_ids`, which the Router reloads live.
- **`scripts/usage-stats-poster.py`** - reads the ignored poster config, gathers the default and valid extra Claude OAuth accounts through the Keychain and Anthropic OAuth boundaries, discovers and deduplicates compatible named/legacy Codex Homes, writes sanitized UTC-slot snapshots to a private SQLite history with advisory locking/retention, and preserves the manual combined embed surface. Automated LaunchAgent runs reuse that bounded text summary and post the original text Usage Report embed once per UTC 30-minute slot through a local ledger, with no image rendering or attachment. Configured DeepSeek homes are reported from their private key instead of the Codex rate-limit request: the poster validates the documented account-wide `GET /user/balance` response (USD/CNY only, all amounts required and preserved exactly) and pairs it with this machine's local DeepSeek token totals in a compact `deepseek (API)` text block that uses an optional `deepseek_balance_references` display budget for an inline used-balance bar with used and remaining percentages and no quota card, while a DeepSeek-backed root Codex session still runs through the Codex app-server.
- **`scripts/usage-dashboard-renderer.py`** - credential-free Pillow renderer for the trend-first PNG; retained for back-compat but no longer invoked by the posting workflow. The text-only poster installer does not require Pillow.
- **Router** - `scripts/router.js` (modules in `scripts/router/`) holds the root token and one discord.js gateway, classifies inbound events for every registered project (whatever its `transport`), and serves sessions over a private Unix socket (`~/.local/state/ccdm/router/`, NDJSON, keyed `hello`). Operations dispatch through `scripts/router/ops/`, one module per family, with Session Scope checked before any op runs; `reply` executes the project webhook (multipart files, a `↪ [jump](…)` first line for `reply_to`, and 2000-character chunks); `edit_message` edits only the project's own webhook messages, and `react`/`typing` act as the bot. Reads (`fetch_messages`, `read_last_x_messages_in_channel`, `export_message_range`) use the bot token, with large reads and exports written to private temporary files; `export_message_range` reuses `scripts/export-discord-range.js`. `download_attachment` returns a signed CDN URL for the session to fetch, from the cached event while fresh or by re-fetching the message. Every `message_id` target is fetched from the session's channel first; anything else is a logged `scope_violation`. `scripts/router/client.js` is the shared client library; it reconnects with capped backoff and fails fast with `router_unavailable` while disconnected. The Router watches `keys/` and revokes any session whose key was replaced, and watches the registry directory to rebuild the routing table after a debounced change (`CCDM_ROUTER_REGISTRY_DEBOUNCE_MS`, default 250 ms); a registry that fails to load keeps the last good table and is reported by `router status`. When a reload moves a connected project's channel, the Router pushes a `scope_changed` event (the new Session Scope) to each of that project's connections; `client.js` validates and adopts it as `client.scope`, and the Codex bridge, its scoped MCP server, and the Claude channel server retarget their inbound filter and implicit tool channel. All Router REST goes through `scripts/router/discord-rest.js`, which queues requests per route bucket, honors bucket headers, `Retry-After`, and the global limit, and fails a request still unsendable after the wait bound (`CCDM_ROUTER_RATE_LIMIT_MAX_WAIT_MS`, default 30 s; `CCDM_ROUTER_RATE_LIMIT_FALLBACK_MS`, default 1 s, when a 429 carries no delay) with the typed `rate_limited` code; repeated `edit_message` calls to one message coalesce to the latest content while an edit is queued or in flight. The Conversation Reminder observer connects with `role: "observer"` and the key in `keys/.observer.key`. It receives every router project-channel message, including webhook and bot messages, plus reactions, and may perform no operation. An owner `/close` goes only to it. Root connects with `role: "root"` and the key in `keys/.root.key`: it receives owner and `root_allowed_user_ids` messages in the registry's `root_channels`, plus the owner's bot mentions and native replies to root-bot messages in router project channels (those never reach the project; a guest's mention reaches no one). Root may target root channels and any registered channel; its `reply` posts as the bot with native replies, and its `edit_message` edits only the bot's own messages. `restart-root-agent.sh` runs root Claude as this client: `ccdm-channel-server.js` with `CCDM_ROUTER_ROLE=root`, launched with root's fresh key and no Discord token, and the launch succeeds only after root's `hello_ok`. `restart-root-codex-agent.sh` runs root Codex as the same client: `codex-bridge.js` in root mode (`CCDM_ROUTER_ROLE=root`, root channels and allowed users from the registry), whose scoped MCP server acts as root over an op-only (`listener: false`) root connection. Both root modes arm `scripts/router/emergency.js` when their Router connection drops: after `CCDM_ROOT_FALLBACK_AFTER_MS` (default 120000) without the Router, root logs in directly with the root token, hears only root channels from the owner and `root_allowed_user_ids` (never project channels, mentions included), and posts a one-line notice in the primary root channel; the Router client's `beforeHello` hook closes that direct client before root's next hello. Root admin scripts keep reading the root token from root's Discord state directory. `router.js migrate-root-config` copies root's no-mention `access.json` groups and allowlisted users into the registry once, leaving `access.json` untouched. `router.js serve` takes `router.lock` in the state directory before anything else, so a second foreground or supervised Router exits non-zero without touching the running one; a lock whose pid is dead is reclaimed. `install-router-service.sh` supervises it as the `com.ccdm.router` LaunchAgent: the read-only `router.js preflight` (Node, registry, root token, socket directory ownership and 0700 mode) must pass before launchd is touched, the rendered plist holds only paths with private logs in the state directory and relaunches only after an unsuccessful exit, and a failed replacement load restores the prior plist and loaded service.
- **Thread Supervisor** - `scripts/thread-supervisor.py run` is the foreground worker (`status` reports it); its modules live in `scripts/thread_supervisor/`, one per concern, with Router events dispatched through a thin table in `dispatch.py`. The worker holds `worker.lock` and a private SQLite store (schema v1, `threads`, `creation_requests`, `boot_buffers`) in `~/.local/state/ccdm/thread-supervisor/`, writes a fresh `keys/.supervisor.key` in the Router state on each start, and spawns `scripts/thread-supervisor-link.js`, the Node link that owns the single `supervisor` Router connection through `client.js` and relays events and op calls as NDJSON over stdio. It has no Discord credential: every Discord action is a Router op. It binds owner-, guest- and requested bot-created threads on `thread_create`. `boot.py` starts a bound thread's Claude session on its first owner or guest message through `scripts/start-thread-session.sh` (in a background thread whose exit returns to the event loop as an internal frame), buffers boot-time messages, and on `thread_session_live` writes the bootstrap the thread-mode channel server (`ccdm-channel-server.js` with `CCDM_THREAD_ID`) waits for before delivering live events. `lifecycle.py` handles `thread_update` archives (stop, then classify the actor from the audit log on a timer whose polls return as internal `archive_poll` frames) and `thread_delete`; a stopped or owner-reopened closed thread resumes its provider conversation with `--resume`. `commands.py` answers in-thread `thread_command`s (`/restart`, `/clear`, `/close`, and `/compact`/`/pause`/`/unpause` with no live session), deferring one that arrives mid-launch until the launcher exits. `config.py` answers `/config` in threads and project channels and applies a pending provider or account change on the owner's ✅ `thread_reaction`.
- **Root emergency operations and request deadlines** - while `scripts/router/emergency.js` is engaged, root's requester sends `reply`, `react`, `typing`, and `edit_message` directly to Discord by running the Router's own root operations with the root token, limited to root channels (edits to the bot's own messages); everything else still goes to the Router and fails as `router_unavailable`. Release drops the direct path before the direct client closes and before root's next hello. Root Codex's separate MCP server follows the bridge's engagement marker (a file in root's launch directory holding the bridge's pid) and builds its own direct dispatcher. Separately, `client.js` sends each request's `deadline_at` (10 s by default; longer per-op budgets for large reads and exports from `deadlines.js`), `server.js` runs the operation under it, and `discord-rest.js` fails a queued or rate-limited call past that deadline as `timeout` before sending.
- **Cutover and retirement** - `scripts/migrate-to-router.sh` (one verified, self-rolling-back project cutover) and `scripts/retire-pool.sh` (dry-run by default; `--apply` removes pool bot members, backs up their state, deletes the `project-bot` role, and strips pool fields) remain for registries that still carry Bot Pool fields; the ordered procedure is in `context/session-management.md`.
- **Registry lock** - every `registry.json` read-modify-write (Node `updateRegistry`, shell/Python `scripts/registry-update.py`) holds the `registry.json.lock` directory and commits by atomic rename with the file's mode kept, so the Router's watcher only sees whole files and no writer loses another's change.
- **E2E harness** - Node's built-in test runner plus fixture binaries and local fakes; default tests never contact Discord or agent services.

## External Dependencies
- `Discord API / discord.js` - the Router's one gateway connection and REST (webhooks, messages, reactions), plus root admin REST for channels, roles, invites, and guest permission overrides. Isolation is the Router's Session Scope, not Discord permissions.
- `Claude Code` - runs Claude project and root sessions with the CCDM development channel (`server:ccdm`), never the official Discord plugin.
- `Codex CLI/app-server` - runs Codex project sessions; the bridge registers a scoped Discord MCP server dynamically.
- `tmux` - owns long-running local sessions and provides the Claude slash-command relay boundary.
- `macOS Keychain / local auth files` - store agent credentials; never copy their contents into tracked files.

## What Does NOT Exist Here
- No web application; durable configuration is JSON and the Usage Stats feature's private SQLite history is local state only. The history writer never traverses or deletes Claude/Codex source logs.
- No daemon supervisor for project sessions; tmux sessions must be restarted after reboot (only the Router, reminder service, and usage poster have LaunchAgents).
- No remote-host orchestration; remote setup commands are handed to the user.
- No real external calls in the default E2E suite; live smoke tests require `CCDM_LIVE_E2E=1`.
