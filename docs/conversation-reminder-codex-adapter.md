# Codex Conversation Reminder adapter v1

This adapter observes a registered Codex Project Conversation. It does not schedule or send Conversation Reminders, close conversation state, or acknowledge `/close` with a checkmark; the [Conversation Reminder service](conversation-reminders.md) does that for both Claude and Codex channels.

## Readiness

Run `python3 scripts/conversation-reminder-readiness.py <project>` from the project root. Add `--json` for the event contract and recent committed events. A ready result means the registered Codex assignment, project bot credential, installed adapter capabilities, and private event receiver pass local checks; recent events show what the running bridge actually observed. The command does not establish that the bot is currently connected to Discord. It reports missing credentials, ambiguous or changed assignments, unsupported providers or receiver state, pending events, and `delivery_enabled: false`. It never prints tokens or message bodies. The default private state directory is `~/.local/state/ccdm/conversation-reminders`; `CCDM_REMINDER_STATE_DIR` can select another private location for a test or operator deployment.

`scripts/conversation-reminder-events.py drain --project-root <root> --state-dir <dir>` retries uncommitted outbox events. The Codex bridge also drains on startup and after every new event. `status --project <project>` is read only. Pending events remain in the private outbox during a receiver outage; rejected and stale records move to a private `rejected/` directory for diagnosis. Event storage contains IDs, timestamps, disposition, and assignment metadata, never conversation text or credentials. Directories and database files are private to the local user.

## Event contract

The event and readiness schema version is `1`. Every event has a unique `event_id`, `event_type`, `project`, `channel_id`, `bot_id`, `assignment_generation`, `provider`, UTC `event_time`, sortable `event_order`, and `adapter_instance_id`. Codex response events also carry `provider_session_id` (Codex thread), `provider_turn_id`, `interaction_id` (the owner message associated with the response), and confirmed Discord `message_id` or `delivered_message_ids`. `source_message_id` identifies the owner message that caused activity. The receiver checks the current registered assignment and returns `committed`, `duplicate`, `stale`, `rejected`, or `retryable_failure`. A duplicate event ID with different metadata is rejected. The producer writes a durable outbox entry before asking the receiver to commit it.

Event types are `owner_activity`, `response_delivered`, `input_needed`, `work_resumed`, `turn_completed`, `session_terminated`, and `close_requested`. Ordinary owner text or attachment input and reactions in the assigned channel are activity; management commands are classified separately. Guest activity is not an owner event. A successful scoped Discord MCP `reply` emits `response_delivered` with its returned message ID. A `reply` can set `conversation_disposition` to `progress` (default) or `input-needed`; the latter must be used only for a question asking the owner to respond, and emits `input_needed` after a successful send. Attachment replies use the same receipt path. The opt-in text fallback records a receipt only after its Discord send succeeds. Tool starts, edits, reactions, failed sends, and regular Codex text deltas do not provide answer receipts. A successful turn completion emits `turn_completed` only with confirmed reply IDs for its latest owner interaction. Bootstrap, compaction, failed/interrupted turns, and retries without qualifying output do not produce completion events. Steering updates interaction correlation after the steer succeeds; queued input receives correlation when its turn starts. Active work resumed after an input-needed question emits `work_resumed`.

The bridge consumes an exact trimmed `/close`, or that command preceded by a permitted assigned or root bot mention, before project and root management dispatch. It consumes guest `/close` without an agent turn; only the registered owner emits `close_requested`. The event is a request for a future durable conversation consumer, not proof that a conversation closed. The adapter reads the versioned private `recorded-reminder-message-ids.json` exclusion list; owner reactions on recorded reminder IDs never enter Codex. This reserves the identity based exclusion for the delivery milestone. A malformed exclusion list fails closed for reaction forwarding.

## Tested runtime and boundaries

Verified locally on 2026-09-24 with Node 22.20.0, Python 3.10.4, and `codex-cli 0.155.1`. The default E2E suite used its fake Codex app-server and fake Discord boundary; it did not invoke a real Codex model or send a real Discord message. The Codex contract is app-server JSON-RPC `thread/start`, `turn/start`, `turn/steer`, `turn/started`, and `turn/completed`; the scoped Discord MCP contract is `tools/call` for `reply`, with the bridge grant and, for root routing, the channel scope grant. Only a successful Discord POST or upload response with a message ID creates a receipt. The inbound contract is Discord `messageCreate` and `messageReactionAdd` filtered to the current assignment and registered owner; `/close` is intercepted before normal routing. The fake suite proves these shapes, while a real provider/Discord compatibility check remains separately gated. Reminder delivery is performed by the separate [Conversation Reminder service](conversation-reminders.md), and only after `enable` confirms that both provider adapters are installed.
